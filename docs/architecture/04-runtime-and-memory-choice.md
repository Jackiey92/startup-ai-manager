# 技术选型：运行时与记忆底座

> 状态：**暂定方案（2026-09-23）**。本文记录为什么选「OpenClaw 运行时 + OpenViking 记忆库 + 自研公司事实层」，以及由此产生的许可证边界。后续若底层项目发生重大变化，以本文为决策回溯依据。

## 一、结论先行

```
┌────────────────────────────────────────────────────────────┐
│  Startup Harness 前端（活状态 GUI）                            │
└───────────────▲────────────────────────────────────────────┘
                │  本项目自有代码（MIT）
┌───────────────┴────────────────────────────────────────────┐
│  公司事实信用层（自研 · 核心壁垒）                              │
│  FactVoucher 台账 · 源文件 span · verified/claimed/inferred  │
│  事务网关 · 血缘 · 外部数据清关                                 │
└───────────────▲────────────────────────────────────────────┘
                │  仅依赖抽象接口 MemoryProvider（能力接缝）
        ┌───────┴────────┐
        │ OpenViking 适配 │  ── HTTP/SDK ──▶ OpenViking（AGPL-3.0，独立部署）
        │ Local 参考实现  │  ── 文件/SQLite（零外部依赖，开箱自托管）
        └────────────────┘

  Agent 运行时底座：OpenClaw（独立进程，编排 / 沙箱 / cron / 工具 / 多渠道）
```

- **Agent 运行时**：OpenClaw
- **记忆存储 / 检索底座**：OpenViking（开源、可自托管，作为独立服务通过 API 调用）
- **公司事实信用层**：自研，置于记忆底座之上，与任何后端解耦
- **备选与参考**：DeepSeek Harness（迁移目标）、Hermes Agent（记忆子系统设计参考）

## 二、选型原则

1. **模型与组件都要可替换**。不绑定单一模型厂商，也不被某个「全家桶」运行时锁死。
2. **借通用运行时，自研垂类壁垒**。会话、沙箱、调度、向量检索等通用能力外采（开源），只自研「公司模型 + 可信记忆」。
3. **一切通过能力接缝（Capability Seam）**。垂类层只依赖抽象接口，换底座 = 换一个适配器，而不是重写业务。
4. **开源必须能自托管**。任何人 clone 本仓库都能跑起来，不强制依赖某个托管服务或私有凭证。

## 四、为什么运行时选 OpenClaw

- **成熟度与开箱体验**：高频迭代、文档完整、生态最大；DSH 仍处 `0.1.x-alpha`，README 明示「会有兼容性破坏性变更」，单人项目不宜押注。
- **渠道即入口**：内置 20+ 聊天渠道（Telegram / Slack / WhatsApp / 飞书 / 微信等）与原生 App，是未来触达创始人的天然分发面，DSH 短期不具备。
- **模型与 harness 可换**：模型适配器以插件形式存在，符合「模型其次、可替换」的判断。

不选 Hermes 运行时的原因：其记忆子系统与运行时强耦合，引入它会被迫牵进整套框架，违背组件解耦原则；且其 open issues 数量庞大（约 4.4 万），复杂度风险高。

## 五、为什么记忆选 OpenViking，而不是 Hermes

| 维度 | OpenViking | Hermes 记忆 |
|---|---|---|
| 形态 | **独立上下文数据库服务**，与运行时解耦 | 与运行时长在一起 |
| 内容 | 记忆 + 知识 RAG + 技能统一文件系统 | 偏「关于你这个人」的个人记忆 |
| 自托管 | Docker / Railway 一键部署 | 可自托管，但更重 |
| 契合点 | 分区天然映射「原文 / 事实 / 外部检疫」信任边界 | WAL / 压缩 / 回溯工程值得借鉴 |

OpenViking 是**独立服务**，可与 OpenClaw 自由组合；Hermes 记忆则会绑死其运行时。架构洁净度上 OpenViking 胜出。Hermes 的 `state / WAL / compaction / readpool / rewind` 设计仅作为自研时的参考。

### MemoryProvider 接缝

垂类层不直接依赖 OpenViking，而是依赖一个抽象接口：

- 原文层：内容寻址（按哈希）的不可变存储读写；
- 事实层：事实台账的提交（事务）与带滤镜的查询（as-of / status / valid_to）。

提供两个实现：

1. **OpenViking 适配器**：调用 OV HTTP/SDK，默认用于生产；
2. **Local 参考实现**：基于本地文件 + SQLite，零外部依赖，保证开源仓开箱可自托管。

## 六、许可证边界（AGPL-3.0，重点）

本项目自身代码为 **MIT**；OpenViking 为 **AGPL-3.0**（强 copyleft，且含网络条款）。为避免传染并合规：

1. **不拷贝、不 vendor、不 fork OV 源码进本仓库**。仓库内只保留「调用 OV API 的适配器」——该部分是本项目自有代码，可按 MIT 许可。
2. **OV 作为独立进程 / 独立镜像部署**，通过网络 API 访问；可用 compose 编排，但应引用官方镜像、不重新分发其代码。
3. **不修改 OV 内核**。FactVoucher 所需的结构化台账、状态机、校验闸门，全部实现为本仓库内的**上层服务**。若确需改动 OV，须将修改按 AGPL 单独公开。
4. **显著声明**：在 README 与分发物中标注 OpenViking 及其 AGPL-3.0 协议，提示用户其自托管 / SaaS 使用需自行遵守该协议（AGPL 网络条款要求通过网络提供修改版时公开修改源码）。

## 七、公司事实层为何永远自研

OpenViking 解决「存得稳、检得准」，Hermes 解决「记住你这个人」，DSH 日志记录「Agent 会话轨迹」——**没有任何一个提供「公司实体—属性—值—源文件 span—verified/claimed/inferred 状态机」这套账务级信用体系**。

因此 FactVoucher 台账、可信写入闸门、血缘追溯、外部数据清关，始终是本项目自研且与底座解耦的核心壁垒：**记忆底座负责存与取，不负责账对不对。**
