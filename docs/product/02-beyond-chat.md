# 产品形态论：对话之后

## 对话不是 Harness 的最终形态

对话窗口强大、通用、零门槛，但它 **不够直接、太过被动**：用户必须主动发问，信息以时间线堆叠，难以一眼看出「现在该关注什么、该我拍板什么」。

一个类比：

> 对话是 Agent 时代的 **CLI**——强大、高密度，但不是普通人每天的主界面；我们要做的是 Agent 时代的 **GUI**：一张主动推送、空间化的「公司状态面」。

## 为什么企业可以做状态面，个人助理却停在对话

不是设计偏好，而是两条客观规律：

1. **有没有可预制的本体**：个人生活没有跨人通用的结构，关系、目标、待办高度主观，只能退回零结构的对话；企业则有一套外部强制的本体——工商、股权、三表、税、订单、合同、社保，这套结构由法律与会计准则定好。
2. **要不要被问责**：企业要对股东、税务、员工负责，需要可回看、可核对、可追责的持久状态面；对话转瞬即逝，扛不起问责。

## 我们做的不是传统 BI 看板

| | 谁维护 | 模式 | 回答 |
|---|---|---|---|
| 传统 BI 看板 | 人配、静态 | 人去翻 | 发生了什么 |
| 纯对话 | 临时 | 拉、被动 | 你问的那句 |
| **活的公司状态面** | Agent 实时写、持续更新 | 推、主动 | 现在该盯什么、该你拍板什么 |

状态面上的每个区块都是可直接「确认 / 追问 / 看出处」的活组件，而不是静态截图。

## 三层形态，同一内核

- **状态面（默认、主动）**：公司怎么样、哪里有雷、待你拍板；
- **对话（按需唤起）**：开放式追问、模糊指令的万能逃逸舱；
- **生成式 UI（按任务即时渲染）**：填表 / 审批 / 对账时，Agent 当场长出所需界面。

## 设计要点

- 默认 push：该关注的顶到眼前，而非等用户来问；
- 把「待你拍板」做成显式的审批队列，不埋进对话；
- 推理可见、来源可信、动手前留人审批点；
- 状态面出错代价高于说错一句话，因此形态丰富度由「可信记忆」与「写入校验」兜底。
